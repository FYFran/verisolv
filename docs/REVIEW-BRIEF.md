## 2. 项目定位（一句话）

> **一个"算完会自己复核自己"的结构仿真与优化智能体。**
>
> 求解器报告"计算成功"不等于结果可信。本项目让 AI 智能体独立完成非线性结构分析，**并且独立判断自己的结果能不能信**；不可信时自动诊断原因、更换方法重算，直到给出经得起复核的答案。

**要解决的问题（真实工程痛点）：**

非线性有限元求解器有两种失败方式：

| 失败方式 | 表现 | 危险程度 |
|---|---|---|
| **明败** | 报错、不收敛 | 尚可——工程师知道出事了 |
| **暗败** | **报告"计算成功"，但结果是错的** | **危险——工程师会采信** |

传统做法是资深工程师盯着残差曲线，凭经验判断"这个结果能不能用"。这有三个问题：**隐性、不可复制、会出错**。本项目把这种判断显式化、自动化、可审计。

**解析解对照**（浅拱双杆桁架，有教科书级闭式解）：

**跨库交叉验证**（与 [PyNiteFEA](https://github.com/JWock82/Pynite) 3.2.0，754★ 独立结构分析库）：

| 端部载荷 | 本求解器 | PyNiteFEA | 相对差 |
|---:|---:|---:|---:|
| 50,000 N | −8.877870 mm | −8.884216 mm | 7.143e-04 |
| 5,000 N | −0.888358 mm | −0.888422 mm | 7.132e-05 |
| 500 N | −0.088842 mm | −0.088842 mm | 7.127e-06 |
| 50 N | −0.008884 mm | −0.008884 mm | 7.097e-07 |
| 5 N | −0.000888 mm | −0.000888 mm | 6.794e-08 |

**载荷每降一个数量级，差距降一个数量级。** 这是几何非线性修正项应随载荷线性趋于零的签名。本求解器保留几何非线性，PyNite 默认分析是线性的，因此二者应在大位移下分离、在小位移下重合。

### 4.3 "暗败"案例（项目的核心论点）

开自适应步长后，载荷控制**会"假装成功"**：

```
step 6:  λ=0.3938   顶点下挠 0.0374 m
step 7:  λ=0.4000   顶点下挠 0.2155 m   ← 一步跳了 0.178 m
```

求解器报告 `converged=True`。**但它跳到了另一条平衡分支上，把平衡路径悄悄走断了。** 相邻步位移增量是中位数的 **1059 倍**。

实测中，AGH 智能体独立运行后**主动拒绝了这个结果**：

> "adaptive load-control run that 'converged' to λ=1.0 was rejected as **suspect** … it silently jumped branches (0.178 m step vs. 0.00017 m median, ~1,059× ratio). **That number is not reported.**"

## 5. 技术架构

```
用户提需求
    ↓
AGH 智能体（agnes-3.0-flash）
    ↓ 调用工具（AGH 记录完整 Trace）
┌──────────────────────────────────────┐
│ ① solve    非线性分析                 │
│ ② verify   四项独立验证               │
│ ③ diagnose 5 类失败分类               │
│ ④ repair   策略升级重跑               │
│ ⑤ re-verify 直到 verified            │
└──────────────────────────────────────┘
    ↓
纯 Python 核心（零 AGH 依赖，可独立运行）
```

### 5.1 四项独立验证

| 检查 | 原理 |
|---|---|
| `residual` | 独立重建残差：把报告的解代回平衡方程 |
| `global_equilibrium` | 全局力/力矩平衡：内力自平衡 ⇒ 支反力 + 外载应为零系统 |
| `path_continuity` | 平衡路径连续性：相邻增量比值检测分支跳变 |
| `step_refinement` | 步长加密复算：不可复现的结果不可信 |

### 5.2 五类失败分类

`max_iterations` / `diverged` / `singular_tangent` / `nonfinite` / `step_exhausted`

诊断逻辑关键点：区分**极限点**与**发散**。特征是残差**先下降后有界振荡**（极限点）还是**持续增长**（发散）。

### 5.3 修复策略升级链

`displacement_control` → `refined_increments` → `line_search` → `robust_combo`

自动选择控制自由度：做一次线性分析，取响应最大的自由度作为控制量。

## 6. 开发过程中被自己的验证层抓出的两个 bug

**这两个案例是"验证不是橡皮图章"的直接证据。**

### Bug 1：力矩用了未变形坐标

优化结果被判 `suspect`，但 `step_refinement` 显示解完全可复现（差 6e-10）。追查发现是**检查本身算错了**：几何非线性下，杆件内力只在**变形后**构型中才共线、才产生零力矩，而我的检查用了参考坐标。

```
修正前  moment imbalance 3.665e-04
修正后  moment imbalance 5.829e-10     ← 降六个数量级
```

### Bug 2：应变的灾难性抵消

小载荷下求解器报 `step_exhausted`（步长耗竭），看似不收敛。实际是数值精度问题：

```python
# 原实现
strain = (L*L - L0*L0) / (2 * L0*L0)
```

小应变下 `L²` 与 `L0²` 都约为 1.0，两者之差约 5e-13——**双精度下两个接近 1.0 的数相减，有效位数全部丢失**。残差因此永远降不到收敛判据以下。

```python
# 修正（代数等价，但无抵消）
# L² - L0² = 2·dX·du + du·du
du = ue[2:4] - ue[0:2]
delta_l_sq = 2.0 * (dx_ref @ du) + (du @ du)
strain = delta_l_sq * 0.5 * inv_l0_sq
```

**发现路径**：跨库交叉验证。修复后小载荷下从"不收敛"变为收敛到 1e-13。

### 附带澄清的一个"假地板"

交叉验证修复后差距在 3e-5 处不再下降。没有接受它，而是做了惯性矩敏感性扫描：

```
极小惯性矩      相对差
   1e-08        3.35e-03
   1e-10        3.36e-05    ← 原取值
   1e-12        2.65e-07
   1e-14        6.79e-08    ← 改用
   1e-16        7.13e-08    ← 触底（PyNite 自身噪声）
```

那个地板是"用框架单元模拟桁架"引入的弯曲柔度，**不是我们的误差**。同时发现**验收判据本身写错了**：原先在 500 N 处卡 1e-6 绝对阈值，但那里的 7e-6 是真实的非线性效应。改为检查"差距随载荷单调收敛"。

## 7. 自我评估：我们真正的贡献是什么（诚实版）

### ✅ 我们确实做到的

1. **一个数值上正确、经多重独立验证的非线性求解器**（解析解 1e-13 / 跨库 6.8e-8）
2. **一个能识别并拒绝"假成功"结果的工作流**——有真实数值证据（1059 倍增量比）
3. **一个 AGH 智能体可以自主驱动的完整工具面**（端到端实测通过，非演示）
4. **自己的验证层抓出了自己代码里的两个 bug**——这是验证有效性的最强证据

### ⚠️ 必须承认的

1. **"静默跳分支"不是我们发现的。** 这是计算力学里的经典现象——弧长法（Riks/Crisfield）上世纪就为此发明了。**我们的贡献不是发现它，而是把它变成一等失败模式，让智能体能识别、拒绝、自动修复。** 这是一个"系统化"贡献，不是"科学发现"。
2. **我们的四项验证并非全部独立。** `residual` 和 `global_equilibrium` 都调用了同一个 `assemble()`——如果单元公式本身错了，两项都会通过。真正独立的是解析解对照和跨库对照。**目前这四项更准确的定位是"自洽性检查"。**
3. **优化算法很朴素。** 292 次评估的坐标模式搜索，没有用梯度、伴随法或遗传算法。
4. **只有 2D 桁架单元。** 没有梁、壳、连续体单元。
5. **"AI 含量"存疑。** 如果去掉智能体，整个流程可以由一个 Shell 脚本编排。智能体的价值在于"诊断"和"策略选择"这类需要判断的环节——但这一点在多大程度上不可替代，是可以质疑的。

## 10. 开放问题（请重点评审）

### Q1. 核心贡献是否成立？
"验证门控的智能体"是一个真贡献，还是"给脚本套了个 LLM 壳"？如果评委问"**去掉 AI，这个项目还能做吗？**"——我们的答案是"能，但需要工程师手动做诊断和策略选择，且无法规模化"。**这个答案够不够？有没有更好的表述，或者我们该补什么才能真正让 AI 不可替代？**

### Q2. 桁架够不够？
只有 2D 桁架单元。正方观点：桁架足以演示极限点、失稳、非收敛，加梁/壳单元是范围蔓延。反方观点：评委可能觉得"桁架太玩具"。**在本科组 25% 看"任务完成度"、只有 10% 看"技术深度"的权重下，加单元类型是不是错的投入方向？**

### Q3. 四项验证的"独立性"问题怎么解？
我们已承认 `residual` 和 `global_equilibrium` 共用同一套 `assemble()`，不是真正独立。**要不要重构？还是说"自洽性检查 + 外部对照"这个组合本身已经足够，只需要在文档里说清楚？有没有成本更低的办法提升独立性？**

### Q4. 弧长法值不值得做？
成本半天。收益：修复策略从"需要猜控制哪个自由度"变成"通用方法"。**在只剩 6 天、且视频和材料都还没做的前提下，这半天该花吗？**

### Q5. 演示视频的叙事成立吗？
我们的钩子是"**求解器报告了成功，它拒绝了那个答案**"。**对非专业评委（可能是 AI 打分）有效吗？** 有没有更有冲击力的切入角度？前 25 秒应该放什么？

### Q6. 优化该做到什么深度？
现在是坐标模式搜索（292 次评估）。要不要上 SLP / 遗传算法 / 伴随法灵敏度？**注意"技术深度"只占 10%，而"任务完成度"占 25%。**

### Q7. 规则风险怎么处理？
- 模型限制矛盾（红头文件严格 vs 页面宽松）：我们选严格。**这个判断对吗？**
- 开发过程使用了 AI 编程助手：规则要求"学生独立完成"，取消资格情形包括"代做"和"隐瞒第三方素材来源"。**该主动披露吗？怎么措辞风险最低？**

### Q8. 6 天计划现实吗？
按你的经验，这个计划哪里最可能崩？**如果只能保 3 件事，应该是哪 3 件？**

### Q9. 有没有我们完全没想到的？
无论是技术上的、策略上的、还是规则上的。
